# 性能排查

“慢”至少包含三件事：操作等待、画面/游戏帧率、资源占用。先分别测，再决定改哪一层。

## 固定比较条件

记录源码提交或发布包 SHA256、Windows 构建号、CPU/GPU/驱动、游戏版本、分辨率、窗口缩放、游戏限帧与其他串流软件状态。选择可重复的同一场景，预热后再记录。

| 场景 | 用途 |
| --- | --- |
| 主机原生运行目标程序 | 游戏自身基线 |
| 仅 RDP 分身，关闭其他串流 | 观察子会话和 RDP 显示的增量 |
| 仅其他串流软件使用同一目标 | 观察串流路径的增量 |
| RDP 与其他串流同时运行 | 观察两条路径的竞争或叠加 |

每次只改变一项。分别记录主机和分身里的游戏进程；不能把跑了两份游戏的总占用与只跑一份的基线直接比较。隐藏、最小化、断开和注销也必须分别标明。

## 操作等待

分开记录“启动进程 → 主窗口可见”“点击连接 → 登录完成”和“确认退出 → 主进程结束”。日志中搜索 `性能计时`，可以看到 App 创建至首帧、窗口构造、连接必要预检、连接等待（含重试或取消）、注销请求下发与资源清理的毫秒数。App 内部计时不包含入口前的单文件解包、运行时加载及 UAC；真实首屏仍需从进程启动或人工双击开始测量。

连接前只采集全部阻塞项与廉价提示，不等待完整扫描。诊断面板仍提供计划任务、启动项和系统文件完整性检查。退出只等 `WTSLogoffSession(wait: false)` 接受请求，Windows 清理会话可在主程序退出后继续；这两种完成时间必须分开记录。关闭系统功能仍等待实际注销。

自带运行时发布关闭 `EnableCompressionInSingleFile`，减少加载程序集时的解压工作，代价是 exe 体积增大；本机库仍可能自解包。框架依赖包本来就不启用该压缩。微软说明压缩有额外启动开销：[单文件压缩](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview#compress-assemblies-in-single-file-apps)。比较时区分首次解包、文件缓存已预热及安全软件扫描，不能把命令行导出语言模板的计时当成完整 UI 或分身登录耗时。

本项目已有 C#、原生 WTS API 与系统 RDP ActiveX 混合实现。语言迁移无法省掉 Windows 登录/注销及外部 COM 的等待。只有测量证实某段 CPU 计算是瓶颈时，才值得评估原生重写；可先试验 [ReadyToRun](https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run) 降低 JIT 工作量，收益与体积代价同样需要测量。

## 帧率与占用

区分游戏报告的帧时间和最终显示到分身或其他串流画面的帧率。游戏渲染快，显示路径仍可能慢。

至少记录各进程 CPU、专用/共享显存，以及 GPU 的 3D、Copy、Video Decode、Video Encode 活动。关注 `DesktopTwin`、目标程序、对应会话的 `dwm` 和其他串流进程；只有主程序的工作集不能代表整个分身成本。

系统提供相应实例时，可记录远程桌面图形计数器。没有计数器或实例不证明没有编码；共享帧缓冲路径上的指标适用性也需要确认。参考 [微软图形性能计数器说明](https://learn.microsoft.com/en-us/azure/virtual-desktop/remotefx-graphics-performance-counters)。

## 图形请求的含义

程序在连接前自动尝试 `EnableFrameBufferRedirection` 和 `EnableHardwareMode`。它们是优化请求，可能独立被拒绝；失败时继续连接，没有额外设置开关。日志只记录写入是否接受。[接口说明](https://learn.microsoft.com/en-us/windows/win32/termserv/imsrdpextendedsettings-property)

不要从这一行日志推断已经共享内存、使用了哪个编解码器、完全没有拷贝或能达到固定刷新率。需要结合实际会话、CPU/GPU 活动和输出帧时间验证。

## 减少工作量的实现选择

游戏鼠标是独立输入通道，切换开关无须重连 RDP。捕获检查只在前台控制且接收端就绪时运行；后台、停用与启动等待不运行该计时器。窗口事件驱动启停，复用会话服务的身份采样，减少重复 WTS 查询。[Windows 能效指南](https://learn.microsoft.com/en-us/windows/apps/performance/power) 建议优先减少背景工作与计时器唤醒。

前台未捕获时只由一个计时器按 250ms 间隔发现光标状态，每次请求不授权输入，回复只更新快照供下一次检查使用。删除回复触发的 UI 排队工作，防止查询与回复形成反馈环；本地输入窗口缺失时停止远端查询，只保留低频本地恢复检查。实际捕获时恢复 32ms 检查和原有活动心跳；显式测试接口持有按键时同样维持活动租约。一次被动状态刷新完成后不会自行继续心跳，后台连被动发现也停止。这些间隔是调度配置，不是端到端延迟保证。

保留有界队列和相邻位移合并，按钮与键盘顺序不变。单一串行收发者复用编解码缓冲和超时来源，接收端一次写出完整状态；输入交换已提供活动与光标证据时不再附加心跳。[Moonlight 的输入实现](https://github.com/moonlight-stream/moonlight-common-c/blob/master/src/InputStream.c) 同样区分可合并移动与必须保序的状态变化。本项目仍保留现有逐笔确认，没有为微基准另建并行通道或批次协议。

未授权并完成释放后，输入两端阻塞等新请求；接收端仅在授权期间运行单次看门狗。主程序没有会话或连接已稳定时不再每 500ms 查询 WTS/SCM，窗口隐藏或登录结束后停止全屏凭据观察。诊断打开/激活不自动启动 SFC，现有“重新检测”动作才请求完整性验证；被新请求替代的排队校验取消等待，取得闸门后仍复核是否过期，避免继续执行已无用的扫描。目标程序启动不等待无关设置落盘；启动任务失败也不继续等待接收端握手逾时。这些边界由查询次数、管道状态及原始错误回归验证，不将其换算成固定节电比例。

代理使用固定 SDK 编译器及 Framework 程序集，按各自源文件增量编译并启用确定性输出。[MSBuild 增量建置](https://learn.microsoft.com/en-us/visualstudio/msbuild/incremental-builds) 与 [Csc 的 Deterministic 选项](https://learn.microsoft.com/en-us/visualstudio/msbuild/csc-task) 是此处的依据。CI 自动验证无修改时不重编代理、强制重建时相同输入仍生成相同字节，不使用硬件相关的毫秒数作为门禁。

这些措施减少喚醒、I/O、配置与编译工作，不等于已测得整机省电比例。输入微基准须记录实际加载的 DLL SHA-256、运行时、单/跨进程、样本数与原始结果；不能换算成真实游戏端到端延迟或 FPS。

输入热路径先删除重复校验、逐字段读写和会话交换的额外异步包装，再用固定环形队列、只读值状态及接收端自有 INPUT 数组减少分配。固定请求/状态帧及逐笔确认继续沿用；没有增加采样任务或回复触发的 UI 调度。

分配回归在预热后执行 10,000 次，使用 `GC.GetAllocatedBytesForCurrentThread`，将初始化与断言放在测量区外。它们要求队列入出、固定帧编解码、状态值解码、原生输入准备及状态编码的测量区间为零托管分配。原生准备测试编译实际接收端源码，检查复用数组和混合输入的 union 清零，但不调用 SendInput；真实 Framework 接收端另以状态/心跳验证帧格式、空闲、撤权和断线。此结果不包含异步 I/O、任务、异常或 SendInput 本身的所有开销。

异步路径另行测量。每次交换返回只消费一次的池化 ValueTask；容量 1 的通知缓冲合并唤醒，一个复用单次计时器替代逐次超时等待，撤权后停用。`RelativeInputAsyncTests` 用可控、无分配的 IO 源分别验证同步完成和实际挂起的写入／分段读取；`InputWakeSignalTests` 验证缓冲、挂起、计时及关闭，Release 预热后的单线程测量区间要求零托管分配。Debug 编译器另外创建调试用的类状态机，同一组功能测试照常执行，交换的零分配断言只针对生产 Release 配置。这些受控测试不能代表内核 IO 的全部开销。

跨线程实测使用独立探针进程，引用实际生产 DLL，以 `GC.GetTotalAllocatedBytes(true)` 记录该主进程所有线程的分配，初始化和结果序列化放在区间外。对端为另一个真实 Framework 接收端进程，仅交换不授权或只授权心跳；分别测传输层、被动会话循环、活动会话循环和密集请求。记录两端 PID、提交、DLL SHA-256、运行时、预热数、每轮样本数、未即时完成次数和原始结果。接收端进程分配不包含在主进程计数中；线程池迁移、计时器回调和运行时缓存可使轮间有小幅差异，不能把局部零分配写成整个通道零分配。

接收端可在独立 Framework 测量宿主中加载未改动的生产程序集、执行其原入口，以 [AppDomain.MonitoringTotalAllocatedMemorySize](https://learn.microsoft.com/en-us/dotnet/api/system.appdomain.monitoringtotalallocatedmemorysize?view=netframework-4.8.1) 记录该域所有线程的累计分配差。测量控制管道只在每轮边界取样，并记录接收端程序集 SHA-256；该计数包含测量宿主的少量开销，应与未包装的真实接收端测试分开报告。

定位分配类型时，先预热，再在测量宿主的 NoGCRegion 中完成固定次数交换，对同一生产接收端做前后两次暂停式 CLRMD 堆对象统计。记录类型的正向数量／字节差，并把控制管道的少量对象单列；不把整个进程转储作为公开测量附件。旧 Framework 管道的同步读写经过逐次 Begin/End 路径，每次交换新建两组 PipeStreamAsyncResult、ManualResetEvent、SafeWaitHandle、IOCompletionCallback 和 Overlapped；连接级原生 IO 复用消除这批逐次对象。

回归测试将真实管道与同一接收循环组合，通过假的注入动作记录键／按钮，不调用 SendInput，覆盖租约续期、读写阻塞、截断／非法帧、EOF、关闭与取消竞态。接收线程的稳态读写单独用线程分配计数检验；真实 Framework 程序另验证身份、空闲、租约及截断帧超时。这里的零分配区间不包含连接初始化、异常、持键集合首次扩容或断线释放时的临时集合。

## 当前证据边界

回归测试覆盖异步控制、旧任务失效、图形属性不支持时继续连接等行为；它们不包含真实游戏负载、显卡矩阵或端到端输入延迟。仓库暂不提供量化性能承诺。提交性能反馈时请附上比较条件和原始测量，而不是只报告“感觉像模拟器”。
