# 性能排查

“慢”至少包含三件事：操作等待、画面/游戏帧率、资源占用。先分别测，再决定改哪一层。

## 固定比较条件

记录源码提交或发布包 SHA256、Windows 构建号、CPU/GPU/驱动、游戏版本、分辨率、窗口缩放、游戏限帧与 UU 状态。选择可重复的同一场景，预热后再记录。

| 场景 | 用途 |
| --- | --- |
| 主机原生运行目标程序 | 游戏自身基线 |
| 仅 RDP 分身，关闭 UU | 观察子会话和 RDP 显示的增量 |
| 仅 UU 使用同一目标 | 观察串流路径的增量 |
| RDP 与 UU 同时运行 | 观察两条路径的竞争或叠加 |

每次只改变一项。分别记录主机和分身里的游戏进程；不能把跑了两份游戏的总占用与只跑一份的基线直接比较。隐藏、最小化、断开和注销也必须分别标明。

## 操作等待

按“发起命令 → RDP 断开/连接 → 会话活动 → 串流目标确认 → 返回结果”记录时间。程序会记录 UU 目标及成败；单次 RDP 尝试、设置重连、UU 确认各有预算，详见 [架构](architecture.md)。

热键已去掉固定 1.6 秒等待，正常由文件事件通知；1.5 秒轮询仍是丢通知时的兜底。若仍有明显响应延迟，应区分请求何时写入、主端何时收到，以及后续系统操作耗时。

## 帧率与占用

区分游戏报告的帧时间和最终显示到分身/UU 画面的帧率。游戏渲染快，显示路径仍可能慢。

至少记录各进程 CPU、专用/共享显存，以及 GPU 的 3D、Copy、Video Decode、Video Encode 活动。关注 `DesktopTwin`、目标程序、对应会话的 `dwm` 和 UU 串流进程；只有主程序的工作集不能代表整个分身成本。

系统提供相应实例时，可记录远程桌面图形计数器。没有计数器或实例不证明没有编码；共享帧缓冲路径上的指标适用性也需要确认。参考 [微软图形性能计数器说明](https://learn.microsoft.com/en-us/azure/virtual-desktop/remotefx-graphics-performance-counters)。

## 图形请求的含义

程序在连接前自动尝试 `EnableFrameBufferRedirection` 和 `EnableHardwareMode`。它们是优化请求，可能独立被拒绝；失败时继续连接，没有额外设置开关。日志只记录写入是否接受。[接口说明](https://learn.microsoft.com/en-us/windows/win32/termserv/imsrdpextendedsettings-property)

不要从这一行日志推断已经共享内存、使用了哪个编解码器、完全没有拷贝或能达到固定刷新率。需要结合实际会话、CPU/GPU 活动和输出帧时间验证。

## 当前证据边界

回归测试覆盖异步控制、旧任务失效、图形属性不支持时继续连接等行为；它们不包含真实游戏负载、显卡矩阵或端到端输入延迟。仓库暂不提供量化性能承诺。提交性能反馈时请附上比较条件和原始测量，而不是只报告“感觉像模拟器”。
